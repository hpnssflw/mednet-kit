# Предложение по развитию дизайн-системы mednet-kit

Дата: 4 ноября 2026 года. Основание: [DESIGN_SYSTEM_AUDIT.md](DESIGN_SYSTEM_AUDIT.md), срез `c40e02a`.

Статус: **предложение для рассмотрения**. Этот файл не меняет действующие правила потребителей и не разрешает реализацию визуальных изменений. Компоненты, токены, стили и AGENTS.md в рамках аудита не изменяются.

## 1. Направление и варианты

Предлагается формализовать существующий mednet: Montserrat, палитра ЦНИИОИЗ, Maia, два канала React/HTML и готовые каркасы. Сначала сделать правила точными и доступными агентам, затем закрыть подтверждённые расхождения, сохраняя визуальный эталон.

| Подход                                                        | Выгода                                                                                | Цена и ограничения                                                                 | Оценка                                                                                           |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Только расширить prose в llms                                 | Самое небольшое изменение                                                             | Агент по-прежнему угадывает props, версии, доступные размеры и применимость правил | Полезный первый шаг, недостаточный конечный контракт                                             |
| Существующие источники + генерируемая metadata + тонкий skill | Единый источник, проверяемые версии, работа без Design Director, минимум новых частей | Нужны schema, extractor integration и безопасный installer                         | **Рекомендуется**                                                                                |
| Отдельный design-system backend/MCP/RAG с копией всех правил  | Сетевой поиск и централизованный runtime                                              | Второй источник правды, инфраструктура, зависимость от сети и синхронизации        | Сейчас не обоснован; возможен только для задач Design Director, которым действительно нужна сеть |

## 2. Как читать статусы

- **Существует (E):** подтверждено кодом/источниками аудита. Это не автоматически доказанная доступность каждого применения.
- **Предлагается (P):** новое правило применения, классификация или способ проверки. Не означает, что уже появился CSS token или prop.
- **Требует решения (A):** изменяет внешний вид, публичный API, владение данными или канал распространения. Реализация после отдельного решения; список в §13.

Термины «body», «surface», «density profile» ниже сначала обозначают роли в документации. Нельзя импортировать их как несуществующие экспорты или передавать в компоненты как новые props.

## 3. Типографика и Montserrat

### 3.1. Роли поверх существующей шкалы

Сохранить `TEXT`, `FONT_WEIGHT`, formula clamp и штатную поставку Montserrat 500/600/700. Семантика HTML и визуальный размер независимы: один h1 на страницу; большой KPI не становится heading только из-за размера.

| Роль                          | Рекомендуемое применение                     | Маппинг на существующее                             | Статус                                                |
| ----------------------------- | -------------------------------------------- | --------------------------------------------------- | ----------------------------------------------------- |
| Заголовок страницы            | Тема текущего экрана                         | h1 + text-h1, 700                                   | E: класс; P: единая роль                              |
| Заголовок раздела             | Крупное смысловое деление                    | h2 + text-h2, 600                                   | E/P                                                   |
| Заголовок подраздела          | Следующий уровень структуры                  | h3 + text-h3 или h4 + text-h4, 600                  | E/P; не выбирать уровень по желаемому размеру         |
| Вводный абзац                 | Короткое пояснение перед основным содержимым | text-lead, 500                                      | E/P                                                   |
| Основной читаемый текст       | Описания, инструкции, prose                  | text-base, 16/24 при корне 16px, 500                | E/P                                                   |
| Интерфейсный текст            | Кнопки, поля desktop, строки данных          | text-sm, 14/21, 500, с исключениями компонента      | E/P                                                   |
| Вторичный текст               | Подсказка или пояснение                      | text-sm + muted-foreground; вес — текущий компонент | E/P; не ослаблять дополнительно opacity               |
| Короткая метка                | Неосновная компактная информация             | text-xs, 13/18.2, если допускает компонент          | E/P; не использовать как общий body dense-режима      |
| CardTitle                     | Локальная подпись карточки                   | Текущий CardTitle 16/24, 500                        | E; не заменять глобальным text-h2 автоматически       |
| Числовое значение             | Сравниваемые количества, суммы, изменения    | Существующий размер текста + tabular-nums           | P: общее правило; tnum подтверждён в поставке         |
| Крупный показатель            | Одно значение с подписью и единицей          | Например, text-h2 на p/span + tabular-nums          | P: рецепт, не новый token; размер проверить на данных |
| Технический идентификатор/код | Где важна посимвольная проверка              | mono только по явно описанному сценарию             | E: font-mono и chart tooltip; P: граница применения   |

Не добавлять второй font family для таблиц по умолчанию. Преимущество Montserrat — идентичность и уже готовая кириллица; ограничение для dense UI — вероятная стоимость ширины длинных строк, которую надо измерять на данных продукта.

### 3.2. Числа и таблицы

Предлагается:

1. Сравниваемые числовые столбцы выравнивать вправо; подписи и заголовки этих столбцов согласовать с данными.
2. Применять `tabular-nums` к количествам, суммам, датам/времени при полезном визуальном сравнении; не ко всему тексту страницы.
3. Форматировать данные через `Intl.NumberFormat('ru-RU', ...)` и соответствующие date APIs проекта. Показывать единицы, точность и смысл отрицательного/нулевого/отсутствующего значения явно.
4. Не кодировать отсутствующие данные как ноль; договориться о подписи и доступном пояснении для «нет данных».
5. Идентификаторы, ведущие нули и коды хранить/выводить строками; не превращать их в числа ради форматирования.
6. Не обрезать значимую дробную часть, знак минуса или единицу. Для длинного имени организации сначала определить ширину и перенос; tooltip не должен быть единственным способом получить обязательную информацию.

Tradeoff: tnum стабилизирует ширину, но расширяет узкие цифры. Нельзя обещать, что добавление tnum всегда увеличит число помещающихся столбцов.

### 3.3. Типографический пилот

Материал: русский текст 2–3 абзаца; таблица 10–20 строк с длинными названиями и числовыми столбцами; форма с label/hint/error; 3 KPI с разной длиной значений. Сравнить **внутри Montserrat**: base/sm, имеющиеся веса, ширину колонки, leading, обычные/табличные цифры. Проверить 320/390 и desktop, 200% текста, текстовые spacing overrides.

Критерии: полные значения доступны, колонки не скачут, строки читаются и сравниваются без неоднозначности, нет потери подписей/ошибок. Для оценки удобства — наблюдение за репрезентативными пользователями, а не только screenshot. Смена семейства, добавление 400 или italic — отдельное решение **A3**, только если пилот выявит конкретную проблему. Поставка 400 не должна предлагаться как «уже существующее» решение `font-normal`.

Начальная prose width **65ch** предлагается как проверяемая настройка рецепта, не как существующий token или норматив для всех экранов. Альтернатива — ограничение в rem; ch лучше отражает метрики шрифта, rem предсказуемее для сетки. Для таблиц/prose применять разные ограничения.

## 4. Spacing и визуальный ритм

**E:** база Tailwind 0.25rem; Maia использует половинные шаги и локальные исключения. **P:** сначала ввести роли композиции в справку, ссылаясь на существующие utilities; не создавать отдельный объект SPACE с копией всей палитры Tailwind.

| Предлагаемая роль | Начальное применение                   | Соответствие при корне 16px | Ограничение                                                      |
| ----------------- | -------------------------------------- | --------------------------- | ---------------------------------------------------------------- |
| inline-tight      | Иконка и короткая подпись              | gap-1 / gap-1.5 = 4/6px     | Внутри готовой кнопки решает сам компонент                       |
| inline            | Действия и связанные короткие элементы | gap-2 = 8px                 | Проверить hit areas и перенос                                    |
| field-internal    | Связанные части собственного блока     | gap-3 = 12px                | Field уже задаёт собственные промежутки                          |
| content-group     | Содержимое панели/небольшая группа     | gap-4 = 16px                | Не заменять им Card spacing                                      |
| group             | Самостоятельные группы                 | gap-6 = 24px                | Соотносить с текущим FieldGroup gap-7                            |
| section           | Разделы страницы                       | gap-8 / gap-12 = 32/48px    | Это P для внешней композиции, не существующие section tokens     |
| page-gutter       | Край контента                          | px-4 / sm:px-6 = 16/24px    | Уже используется header/footer; content main выбирается рецептом |

Смысловая группировка важнее одинакового числа: расстояние между группами больше внутреннего. Не исправлять gap-7, px-3.5 или checkbox offsets ради «чистого 8px grid». Если роли начинают повторяться в обоих слоях и не выражаются доступными средствами, тогда можно согласовать семантические spacing exports; сейчас отдельный новый namespace не обязателен.

## 5. Размеры и плотность

### 5.1. Сохранить фактические размеры

Button xs/sm/default/lg = 24/32/36/40px; Input default 36px; Select/NativeSelect sm/default = 32/36px. Размеры указываются как соответствие существующих API, не единая `size="md"` для всех компонентов.

TableHead 48px и ячейка p-3 не задают фиксированную row height: многострочный текст/интерактивный контент меняет строку. Checkbox/radio/switch описывать двумя величинами: видимый размер и фактическая область взаимодействия с учётом `::after`/label/clipping. Не требовать превращения визуального знака 16px в квадрат 44px.

### 5.2. Профили как рецепты, не новый runtime API

У Questionnaire actions уже есть локальный min-h-11 (44px) до sm; это поведение нужно сохранить и учесть при формализации touch-профиля.

| Профиль P             | Состав из имеющихся средств                                                               | Что пока не покрыто                                                                        |
| --------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Стандартный           | Button default, Input 36, Select default, Card default, текущая Table                     | Это действующий baseline, а не новая appearance                                            |
| Компактная композиция | Card sm, Button sm для вторичных действий, Select sm там, где уместен; text-sm для данных | У Input нет sm; таблица не имеет готового density prop; не обещать глобальное переключение |
| Для частого touch     | На текущем этапе выбирать более крупные существующие контролы и просторную композицию     | Button lg = 40px; профиль с целями >=44px потребует отдельного решения/API                 |

**A2:** нужна ли единая touch/compact система, и для каких продуктов. Предлагаемый ориентир 44px для основных touch-действий — продуктовая рекомендация, а не минимальное требование WCAG 2.2 AA и не существующий размер Button. Локальное M про 24×24 остаётся действующим. Новые размеры не следует имитировать потребительскими overrides вопреки справке кита.

## 6. Layout и responsive

**E:** PublicLayout, AppShell, header/footer max-w-7xl, стандартные breakpoints и container queries. **P:** четыре композиционные роли без нового Layout engine:

| Роль                  | Принцип                                                                                                          |
| --------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Public content        | PublicLayout + явно ограниченный content container; align с header/footer там, где это часть композиции          |
| Reading/form          | Более узкий столбец, подписи над полями, связанные группы и заметный submit                                      |
| Application workspace | AppShell, h1 в содержимом, toolbar и основной рабочий блок; боковая навигация остаётся слоем shell               |
| Data canvas           | Доступная ширина для таблицы/графика, локальный scroll в нужном блоке; не ограничивать всю аналитику prose-width |

Рецепты должны определять перенос search/filter/action toolbar, порядок действий на узком экране и сохранение контекста при открытии mobile Sheet. Сначала один столбец; дополнительные колонки — по способности содержимого помещаться. 12-колоночная сетка не обязательна для всех экранов. Не вводить новый breakpoint ради конкретного device name, если проблему решают flex-wrap, min-width и существующая container query.

Сохранить sm/md/lg/xl/2xl. Отдельно проверить границу 767/768 при изменённом корневом font-size: hook Sidebar в px и CSS md в rem имеют разные основания.

Матрица адаптивности: 320/390, 767/768, 1024, 1440 CSS px; длинные русские строки; текст 200%; reflow 320 CSS px/эквивалент 400% zoom; открытые overlays; sticky elements и keyboard focus. Для таблиц допускается локальная двумерная прокрутка по смыслу, но остальной экран должен перестраиваться.

## 7. Радиусы, границы, elevation

### 7.1. Геометрия

**E:** текущие формы Maia работают как система семейств: controls 4xl, card/menu 2xl, dialog 4xl, checkbox 6px, круглые avatar/switch. **P:** описать эти семейства как visual roles и явно показать фактические значения/источники.

`--radius-sm/md/lg/xl` и оставшиеся Tailwind 2xl/3xl/4xl нельзя выдавать за единую возрастающую шкалу. Для собственного блока потребитель следует одобренному рецепту; агент не выбирает «более красивый rounded-*» произвольно.

Альтернативы **A4**:

- **Зафиксировать фактическое поведение и исключения.** Сохраняет вид, минимальная миграция; naming остаётся неидеальным. Рекомендуется первым этапом.
- **Ввести новые семантические aliases, сохранив их вычисленные значения.** Улучшит понятность без обязательной визуальной смены; дополнительный публичный API требует обоснования и additive release.
- **Выправить существующие значения или перевести все компоненты на одну шкалу.** Может изменить nested corners и множество экранов; нужен визуальный пилот, обе реализации и major, если меняется существующий вид бренда.

### 7.2. Границы и фокус

Сохранить роли: `border` для разделения поверхностей, `input` для границы поля, `ring` для фокуса, `destructive` для ошибки. Не использовать слабый декоративный border как единственную необходимую информацию о состоянии. Не подменять `ring` на primary: blue focus — действующая идентичность и смысл.

Проверять реальный composite alpha и соседний фон, а не только исходный token. Фокус должен быть видимым при клавиатуре и не скрытым sticky/overlay. WCAG 2.4.13 Focus Appearance — AAA; не представлять его как обязательный AA без отдельного принятия более строгой цели.

### 7.3. Тени и слои

Сохранить warm sm/md/lg и явно описать, что xl/2xl у floating-компонентов сейчас стандартные Tailwind. Предложенная классификация:

- Обычная поверхность: без elevation, граница/ring текущего компонента.
- Приподнятый собственный блок: только существующая допустимая shadow role из рецепта.
- Floating/overlay: тень и z-index задаёт готовый компонент, не ручной z-9999.

Это классификация, не новые shadow values. Перевод всех floating shadows в тёплый тон или новое z-index token family — **A4** после доказанного конфликта, не обязательная инфраструктура. Сохранить root `relative`/`isolate`, portal и Toaster composition из справки.

## 8. Цвета и темы

Сохранить существующие semantic roles, primary/destructive distinction, отдельные field/input, status triples и `.dark` на html как общий путь для React/HTML. Выбор темы и сохранение preference остаются у приложения. Компоненты не должны получать набор локально придуманных dark-цветов.

Предлагается матрица использования:

| Контекст                | Роли                                                                | Проверка                                                    |
| ----------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------- |
| Основное действие       | primary + primary-foreground; hover primary-hover                   | Default/hover/focus/disabled в обеих темах                  |
| Ошибка поля             | destructive, текст ошибки, aria-invalid, связь через describedby    | Сообщение доступно без различения цвета                     |
| Статус                  | success/info/warning/destructive и соответствующие foreground/muted | Текст/значок, а не только цвет                              |
| Нейтральная поверхность | background/card/popover/muted                                       | Контраст текста и ясная группировка                         |
| Фокус                   | ring с фактической opacity и border текущего контрола               | Видимость на всех используемых фонах                        |
| Ряды графика            | chart-1…8                                                           | Соседние серии, фон, маркеры, подписи, доступное содержание |

**A5:** графики. Рекомендуется сначала проверить возможность сохранить пастельные fills с различимыми контурами/маркерами/patterns и текстовым объяснением. Альтернатива — отдельные semantic роли для chart stroke/fill с подтверждёнными contrast pairs. Изменять нынешние chart-1…8 глобально без оценки всех потребителей не следует; новые значения в этом предложении намеренно не назначаются.

## 9. Interaction, UX и accessibility

### 9.1. Базовый стандарт

Сохранить существующие M/S-правила `docs/agent-guide/ux.md`: labels над полями, submit-time validation с оговорёнными исключениями, noValidate, сохранение введённого, summary ошибок, безопасное подтверждение, раздельные loading/empty/error. Этот документ не отменяет их и не заменяет сроками/ритуалами Design Director.

Уточнения P для рецептов:

- Отдельно задать id/label association, description/error association и aria-invalid; один FieldError не создаёт все связи автоматически.
- У обязательного поля сохранить доступное сообщение об обязательности и при необходимости `aria-required`, даже если native `required` исключён действующим UX-правилом.
- На submit/error focus переносить по рецепту, учитывать announcements; не объявлять каждое нажатие alert-сообщением.
- Pending не менять ширину/смысл кнопки неожиданно; предотвращать повторный запрос на уровне состояния и модели данных, обозначать занятость доступным способом. У Button нет встроенного `loading` prop.
- Для Dialog/AlertDialog задать title/description, начальный и возвращаемый focus; для опасного действия — безопасный default согласно текущей UX-справке.
- Для таблицы нужны caption/label, scope для заголовков, aria-sort у сортируемого столбца; визуальный Table не предоставляет sorting engine.
- Для графиков нужны смысловой summary и доступное представление ключевых данных. Цветовая легенда не заменяет объяснение показателя/единицы.

### 9.2. Motion и обратная связь

**E:** tokens 150/250ms плюс upstream exceptions. **P:** составить inventory фактических animation/transition families и привести обещание reduced motion в соответствие с реализацией. При уменьшении движения убрать декоративные pulse/spin/transform, сохранив статический текст/другую индикацию статуса и корректное завершение lifecycle событий. Способ исправления и объём визуального изменения согласовать до кода; generated TSX руками не менять.

Не делать «все duration = token» самоцелью. Анимация появления, перетаскивание и постоянная индикация имеют разные задачи. Проверять отдельно motion preference и возможность остановить длительное автообновление.

### 9.3. Тестовый стандарт

Основной acceptance набор: keyboard flow, видимый/неперекрытый focus, accessible names и error links, reduced motion, 200% текста/reflow, обе темы, длинные строки, применимые состояния. Проверка text-spacing: пользовательские line-height 1.5, paragraph spacing 2em, letter spacing 0.12em и word spacing 0.16em не должны терять содержание; это проверка устойчивости, не требование таких значений в штатном дизайне. [W3C Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html).

Автоматический axe/lint дополнять реальными сценариями. Chrome 109 проверять отдельно от современного Chrome; source compilation и успешный PostCSS unit test не заменяют целевой браузер. Не восстанавливать удалённый apps/docs ради тестов: использовать playground или разрешённые изолированные fixtures.

## 10. Композиционные patterns

Patterns — знания о сборке компонентов, не новый конкурирующий UI layer.

| Pattern P                    | Существующие части                                     | Обязательная информация/проверка                                   |
| ---------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------ |
| Поле с ошибкой               | Field, FieldLabel, Input, FieldDescription, FieldError | Явные id/for/describedby, aria-invalid, значение сохраняется       |
| Форма с несколькими ошибками | FieldGroup/FieldSet, Alert destructive, Button         | Summary links и focus, page title error prefix, server validation  |
| Список с поиском             | Input/Combobox, Table или Item, Empty, Pagination      | Различать отсутствие данных и отсутствие совпадений; reset filters |
| Dashboard                    | AppShell, Card, Chart/числовые роли                    | У каждого блока loading/empty/error, единица/период, data summary  |
| Публичная страница           | PublicLayout, text-h*, Button/ссылка с buttonVariants  | Один h1, content width, focus и wrapping navigation                |
| Опасное действие             | AlertDialog, Action/Cancel, toast для применимого undo | Объект и последствие, безопасный default, восстановление focus     |
| Async действие               | Button, Spinner/Progress, Alert/Toast                  | Busy state, предотвращение дубля, success/error и повтор           |

Код примеров должен использовать только реальные публичные imports, `render` там, где это API части, и реальные значения variants. Примеры React и HTML отличаются API, но должны сохранять смысл и согласованный вид. Их место — пакетные источники знаний и внешний playground; root proposal не становится третьим каталогом реализаций.

## 11. Владение знаниями и граница Design Director

Кит владеет значениями, API, constraints, примерами и принятой локальной UX-базой. Design Director владеет исследованием контекста, выбором композиции для задачи, references, art direction и критикой результата. Design Director запрашивает capabilities кита и ссылается на rule/pattern IDs; не записывает у себя «Button = 36px, primary = …» как независимую норму.

Общие UX-знания в ките уже существуют. Рекомендуется сохранить их как переносимый baseline, чтобы продукт работал без Director. Не переносить/удалять их сейчас. **A7:** долгосрочное владение общими UX-рецептами, если Director уже содержит аналогичную базу; варианты — ссылки на kit baseline либо согласованное разделение general reasoning и kit-specific acceptance. Любая копия должна быть сгенерированным представлением одного источника, а не второй редактируемой версией.

## 12. Принятие и сопровождение

Для каждой будущей правки фиксировать источник, проверяемое поведение, какие surface/темы затронуты и release impact. Первоочередные документы должны исправлять неточные обещания, но не ослаблять незаметно обязательные UX-правила.

Изменение видимых package styles делается на обеих сторонах `ui/src/brand.css` и `css/src/overrides.css`; generated components обновляются только разрешённым pipeline. Изменение правила потребителя требует соответствующей правки `docs/agent-guide`/пакетных `llms/*`, генерации guides и changeset по действующим правилам. Эти действия не выполнены данным предложением.
